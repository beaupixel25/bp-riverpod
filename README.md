# bp-riverpod

A riverpod sample app

A Flutter monorepo: Melos workspace, Clean Architecture, a shared `core`
package, and one flavored app package per app.

- **core** — shared domain, DI plumbing, theme/design-system, components
- **hello** — app package

## Getting Started

Initialize the project after it is scaffolded:

```bash
melos bs            # Bootstrap the workspace
melos pub-get       # Get dependencies for all packages
melos build         # Run code generation in all packages
```

Then run an app:

```bash
melos hello   # Prompts for flavor and device
```

## Architecture at a glance

| Concern | This workspace |
|---|---|
| Workspace | Melos 8 + Dart pub workspace. Every package lives in `packages/`; there is no `melos.yaml` (Melos 6+ reads the `melos:` section of the root `pubspec.yaml`). |
| Application architecture | Clean Architecture — `domain` / `data` / `presentation`, one folder per feature. |
| Shared code | `packages/core` — bootstrap, error handling, theme/design-system, reusable components, base classes. Every app package depends on it. |
| State management | Riverpod 3 — one `@riverpod` `Notifier` (a *controller*) per page, state modelled as `AsyncValue<T>` |
| Dependency injection | Riverpod providers **are** the container. Bindings are provider functions; the graph is composed at the root `ProviderScope` |
| Routing | `go_router` with typed routes (`@TypedGoRoute` → `routes.g.dart`). |
| Flavors | `development` / `staging` / `production`, one entrypoint each, plus `main_test.dart`. |
| Code generation | `build_runner`: `freezed`, `json_serializable`, `go_router_builder`, `riverpod_generator` |
| `core` exports | `full` — a single `core.dart` barrel re-exporting everything under `src/` |

State management is a **monorepo-level** property: `packages/core` itself is
built around it (the `bootstrap()` signature, the observer, the error-handling
helper, the environment enum), so every app package in this workspace uses the
same setup.

### 4. Inside a feature — how a dependency resolves

```
  LoginPage (ConsumerStatefulWidget)                          presentation
    ├─ ref.watch(loginControllerProvider)          ──▶ AsyncValue<AuthToken?>  (state)
    └─ ref.watch(loginControllerProvider.notifier) ──▶ LoginController        (@riverpod)
          └─ build(): ref.watch(loginUseCaseProvider)  ──▶ LoginUseCase        domain
                └─ ref.watch(onboardingRepositoryProvider)
                      │     └─ ref.watch(buildConfigurationProvider).baseEndpointUrl
                      └─ IOnboardingRepository ....... the seam (domain contract)
                            ├─ OnboardingRepository ......... default binding      data
                            └─ MockOnboardingRepository ..... override for `test`
```

`buildConfigurationProvider` is read in two places, and both are worth copying
when you add a feature: `lib/app/view/app.dart` reads `.appTitle` straight from
a `ConsumerState`, and `onboarding_providers.dart` reads `.baseEndpointUrl`
and passes it to the repository constructor — the repository stays plain Dart
with no `Ref`, so a test can build it directly.

The page never names a concrete repository, and the controller never names a
provider outside `build()`. Which implementation backs
`IOnboardingRepository` is decided entirely by the `Environment` passed to
`bootstrap` in step (1).

### 5. The dependency rule

```
        Presentation  ──────▶  Domain  ◀──────  Data
     (controllers, widgets)     (entities,        (models,
                             DTOs, use cases,   repository
                             repository IFs)    implementations)
```

- **Domain** depends on nothing but `core`'s base classes. No Flutter, no HTTP,
  no JSON.
- **Data** implements the repository interfaces the domain declares, and maps
  external payloads into domain types.
- **Presentation** depends on domain use cases only. It never imports `data/`.
- `presentation` and `data` never reference each other. The abstract repository
  in `domain/repositories/` is the seam, and the provider in `di/` is where dependency inversion actually happens.

Cross-package: `packages/hello` depends on `packages/core`; `core` never depends
on an app.

### 6. Error handling

#### One failure, end to end

Follow a single real failure: someone signs up with an address that already has
an account, and the backend answers `409` with
`{"error":{"code":"EMAIL_ALREADY_REGISTERED"}}`.

1. **The wire.** `ApiClient._decode` sees a non-2xx status. `_ApiError.from`
   reads the body *defensively* — an error response is the least trustworthy
   thing a server sends — probing `error.code`, then `code`, then `error_code`,
   and falling back to the HTTP status if none is there or the body will not
   parse at all.
2. **The typed throw.** The status picks the *kind*: `409` is not 401/403/404
   and not ≥500, so it becomes an `UnknownException`; a `422` would be a
   `ValidationException`, a `401` an `UnauthorizedException`. The backend's code
   rides along in `AppException.code`, and the developer-facing detail
   (`HTTP 409: …`) in `message`.
3. **The data boundary.** `BaseRepository.guard` catches it, sees it is already
   an `AppException`, and rethrows it unchanged with
   `Error.throwWithStackTrace` so the original trace survives. Transport
   failures (`SocketException`, `TimeoutException`) and an unparseable *success*
   body enter the vocabulary here instead — that split is deliberate, and
   mapping status codes in both places is how two mappings drift apart.
4. **The domain.** `UseCase.execute` rethrows an `AppException` untouched and
   wraps anything else in an `UnknownException`. Only an `AppException` ever
   reaches presentation.
5. **The state holder.** `ref.guardAppException` catches `AppException` **and nothing
   else** and records it as state. Assigning that `AsyncError` to `state`
   fires `AppProviderObserver.providerDidFail`, and **that** is what
   breadcrumbs it — one reporting site, so a captured failure cannot be filed
   twice. `guardAppException` deliberately reports nothing itself, and the
   observer holds the same instance `bootstrap` bound to
   `errorReporterProvider`. Anything that is not an `AppException` keeps
   travelling — out of the callback, out of the frame, into the global net.
6. **The sentence.** `failure.toUserMessage(AppErrorMessages(context.l10n))`
   asks `forCode('EMAIL_ALREADY_REGISTERED')` first, which resolves
   `l10n.errorEmailAlreadyRegistered` — "That email already has an account. Log
   in instead." An uncoded failure, or a code this app does not recognise,
   falls back to the type: `NetworkException` → `errorNetwork`, and so on.
7. **The sink.** Sentry (or Crashlytics, or whatever you wire) sees this as a
   *breadcrumb*, not an issue: the user got a sentence and the app carried on.
   `reportHandled` logs no stack trace, which is the visible difference.
   Had the failure not been an `AppException`, it would have arrived through
   `ErrorReporter.report` as a crash, with its stack trace.

#### What each layer may and may not do

| Layer | Its job | What it must never do |
|---|---|---|
| `ApiClient` | status → exception kind, backend code → `AppException.code` | know a sentence, or map transport/parse failures |
| `BaseRepository.guard` | raw error → typed `AppException`, trace preserved | `catch (_)`, or re-map what `ApiClient` already typed |
| `UseCase.execute` | rethrow typed, wrap untyped | swallow anything |
| `guardAppException` | typed failure → state | catch anything that is not an `AppException` |
| `AppProviderObserver` | every provider failure → one lane: breadcrumb if typed, crash if not | report a failure `guardAppException` already reported |
| `AppErrorMessages` | code → sentence, else type → sentence | show `message` verbatim |
| `ErrorReporter` | crashes as issues, handled failures as breadcrumbs | live in `core` as a vendor SDK |

Four rules follow, and breaking any of them is what turns a reportable crash
into a silent one:

- **Translate once, at the data boundary.** `guard()` is the only place a raw
  error becomes an `AppException`. A bare `catch (_)` anywhere else discards the
  cause and the stack trace the reporter needs.
- **Catch only what you can act on.** `guardAppException` deliberately catches
  `AppException` and nothing else, so a genuine bug reaches the global net
  instead of being rendered as "something went wrong".
- **Never show a raw message.** `toUserMessage` decides what a user reads;
  `ServerException`, `CacheException` and `UnknownException` map to the generic
  string on purpose, and `AppException.message` is for logs.
- **One mapper, and it is the localized one.** New copy is a backend code plus
  an ARB entry, never a second `switch` on exception type. A feature-local copy
  layer looks harmless and silently shadows `toUserMessage`, which is how every
  `error*` string in the ARBs can end up unreachable while the app still looks
  correct.

#### Wiring a real sink

`core` never depends on a crash reporter. Out of the box `bootstrap` builds a
`ConsoleErrorReporter`, which writes both lanes to the developer log. To send
them somewhere real, implement `ErrorReporter` in your app:

```dart
class SentryErrorReporter extends ErrorReporter {
  const SentryErrorReporter();

  @override
  Future<void> report(
    Object error,
    StackTrace stackTrace, {
    bool handled = false,
    StackTrace? handledAt,
    StackTrace? invokedAt,
  }) async {
    if (!handled) {
      await Sentry.captureException(error, stackTrace: stackTrace);
      return;
    }
    Sentry.addBreadcrumb(
      Breadcrumb(
        message: '$error',
        data: {'handledAt': '$handledAt', 'invokedAt': '$invokedAt'},
      ),
    );
  }
}
```

**One method, and `extends` rather than `implements`.** Both lanes arrive at
`report`; `handled` tells them apart. `reportHandled` is concrete on
`ErrorReporter` and funnels into `report` with `handled: true`, so extending
gets you that for free — `implements` takes the interface and not the
implementation, which would put the funnel back on you to reproduce.

`reportHandled` gets three stacks and they answer three questions.
`error.stackTrace` is where the failure was **thrown**; `handledAt` is the
code that **handled** it; `invokedAt` is what **started** the action. A count
of breadcrumbs tells you how often something breaks; the three together tell
you whether whatever is already catching it is good enough, and which screen
it came from. `ConsoleErrorReporter` prints one frame of each, as a tree
under the header (`package:` paths elided here for width):

```text
handled: ServerException(message: null, code: 500, cause: null)
├─ thrown at:  OrdersRepository.fetch (orders_repository.dart:41:7)
├─ handled at: AppProviderObserver.providerDidFail (app_provider_observer.dart:78:11)
└─ invoked at: OrdersController.load (orders_controller.dart:31:5)
```

The first two are frame 0 and unfiltered. `guard` rethrows with
`Error.throwWithStackTrace`, so frame 0 of `error.stackTrace` *is* the throw
site; `handledAt` is captured inside the `on AppException` catch, so frame 0
of it is the handler. `invokedAt` is the one that skips frames — whoever
captured it is itself the top of that trace, so `core` and the
state-management package are stepped over to reach your call site.

The three rows are coloured whenever `ConsoleErrorReporter.colored` is on,
which it is by default in debug and off in release. Turn it off with `const ConsoleErrorReporter(colored: false)`
where escape codes are noise rather than colour: a log file, a CI job, or a
debug build on a device writing to logcat.

Then add one line to whichever `main_<flavor>.dart` should use it — the rest of
the call stays exactly as generated:

```dart
await bootstrap(
  () => const MyApp(),
  reporter: const SentryErrorReporter(),
  // ...
);
```

**One door, not two.** `bootstrap` owns the instance: it installs that object
in the global error net, hands it to `AppProviderObserver`, and binds it to `errorReporterProvider` at the root scope. The crash lane and the
handled lane therefore report to the same object, and there is no second place
to remember to wire. Pass nothing and the console reporter arrives the same way.

The moment it is bound matters: the root scope does not exist until `overridesBuilder` has returned.
A failure captured before that point breadcrumbs to a no-op rather than to your
sink — a window of a few milliseconds during composition, and the reason
`bootstrap`'s own `try`/`catch` reports composition failures directly rather
than relying on the handled lane.

**Where configuration actually lives.** `BuildConfiguration` (freezed, in
`core`) holds the per-flavor settings. `buildConfigurationProvider` in `core` is
a deliberately unimplemented placeholder: reading it without an override throws.
`buildOverrides` supplies the real value based on the `Environment` from
`main_<flavor>.dart`, so anything that needs the base URL just does
`ref.watch(buildConfigurationProvider)`. `test/di/overrides_test.dart` asserts
the whole graph resolves for **every** `Environment` — a forgotten override
fails a test instead of shipping.

**The cold start is a decision, not a fixed hand-off.** `/` always resolves to
`LaunchRoute` first; `/landing` and `/main` are both reachable, but neither is
where the app starts. Signed out lands on `/landing` (`LandingRoute`, inside
`features/onboarding/`), signed in lands on `/main` (`HomeRoute`, app-level,
hosting `HomePage`). `/landing` is stage three of the same sequence, on a
timeline of its own (0–1450ms, starting fresh on every build, not a
continuation of the launch's): the ambient wash settles out of a 1.05 scale,
then the sheet lifts 26px off the bottom edge with its five rows staggering in
behind it. The brand lockup is the one thing that does *not* animate — it
arrives already at rest, in the position the launch left it.

## Implementing a new feature

**The short answer: run the `implement-feature` skill.** It interviews you for
the feature's entities, DTOs, use cases, repository API and screens, writes the
baseline slice, edits all three layers, generates extra pages and components,
wires `go_router` and the DI overrides, and runs the build.

```
/implement-feature
```

The same steps in order, and what each one is for:

1. **Generate the slice** — the `/implement-feature` skill writes
   `domain/` (entity, DTO, repository interface, use cases), `data/`
   (model, real + mock repository), `di/` (providers + overrides) and
   `presentation/` (page + controller), and adds any missing codegen deps to
   the app's `pubspec.yaml`.
2. **Shape the domain** — edit the entity/DTO fields and the repository
   interface first. Everything else follows from the contract.
3. **Implement the data layer** — the real repository (and keep the mock in
   `data/repositories/mock/` in sync, since the `test` environment resolves it).
4. **Declare the bindings** — add providers to `features/<f>/di/<f>_providers.dart`,
   typed as the *domain* contract.
5. **Wire the composition root** — add `...<feature>Overrides(environment)` to
   `lib/di/overrides.dart`. Skipping this is
   silent: the feature simply uses the real repository everywhere, including in
   tests. Add its providers to `test/di/overrides_test.dart` so the omission
   fails a test instead.
6. **Build the UI** — page + controller. The controller resolves its use cases
   in `build()` and exposes methods; the page watches state.
7. **Wire routing** — create `presentation/routing/<feature>_routes.dart` with
   a `@TypedGoRoute` class per page and a `List<RouteBase> <feature>Routes`
   collecting them, then spread that list into `appRoutes` in
   `lib/routing/routes.dart`.
   `lib/app/view/app.dart` is never touched — it reads `appRoutes` and never
   names an individual route.
8. **Regenerate and check** — `melos build && melos analyze`.

Where each step lands in the diagram: steps 1–3 are the *domain* and *data*
layers of "Inside a feature"; steps 4–5 are nodes (6) and (5) of the runtime
diagram; the UI steps are nodes (9) and (10).

## Architecture reference

### Layers

Dependencies point **inward** — outer layers depend on inner layers, never the
reverse. See [The dependency rule](#5-the-dependency-rule) for the diagram.

- **Domain** — the innermost layer. Pure Dart with no Flutter, no HTTP, no
  JSON. Holds entities, DTOs, repository *interfaces*, and use cases. It knows
  nothing about how data is fetched or how it is displayed.
- **Data** — implements the repository interfaces declared in domain. Talks to
  external systems (APIs, storage) and maps their payloads into domain types
  via models.
- **Presentation** — Flutter widgets driven by controllers. Depends on domain
  use cases only; it never imports the data layer directly.

### State management (Riverpod)

Each page has a **controller**: a `@riverpod` `Notifier` whose state is an
`AsyncValue<T>`. There is no separate status enum — `AsyncValue` already encodes
idle / loading / data / error, and keeps the previous value across a failure:

```dart
@riverpod
class LoginController extends _$LoginController {
  // `late`, never `late final`: the notifier instance outlives a rebuild while
  // build() runs again.
  late LoginUseCase _loginUseCase;

  @override
  FutureOr<AuthToken?> build() {
    _loginUseCase = ref.watch(loginUseCaseProvider);  // deps resolved ONCE, here
    return null;                                      // data(null) == idle
  }

  Future<void> submit({required String email, required String password}) async {
    state = const AsyncValue.loading();
    // Only an AppException becomes error state; anything else escapes to the
    // observer instead of being swallowed.
    state = await ref.guardAppException(() => _loginUseCase.execute(input: email));
  }
}
```

The page renders with `ref.watch` and handles one-shot outcomes (snackbars,
navigation) with `ref.listen`. A controller depends only on use cases — never on
a repository directly.

### Dependency injection (Riverpod providers)

Riverpod is the container. There is no service locator and no central generated
registry — bindings are ordinary functions, split across two files per feature:

```dart
// features/onboarding/di/onboarding_providers.dart — DEFAULTS
// Typed as the domain contract: this is where dependency inversion happens.
@Riverpod(keepAlive: true)                       // == @LazySingleton
IOnboardingRepository onboardingRepository(Ref ref) =>
    OnboardingRepository();

@Riverpod(keepAlive: true)
LoginUseCase loginUseCase(Ref ref) =>
    LoginUseCase(ref.watch(onboardingRepositoryProvider));
```

```dart
// features/onboarding/di/onboarding_overrides.dart — DEVIATIONS
// Exhaustive: adding an Environment is a compile error here, not a runtime
// "no registration found".
List<Override> onboardingOverrides(Environment environment) =>
    switch (environment) {
      Environment.test => [
          onboardingRepositoryProvider
              .overrideWith((ref) => MockOnboardingRepository()),
        ],
      Environment.local ||
      Environment.development ||
      Environment.staging ||
      Environment.production => const <Override>[],
    };
```

The app's `lib/di/overrides.dart` collects those lists and `bootstrap` applies
them to the root `ProviderScope`. Because overrides are applied at the root
rather than branched inside a provider, a release build tree-shakes away the
mock it never names.

Repositories and use cases stay **plain Dart with constructor parameters**, so a
test can build them directly with no Riverpod involved. Run `melos build` after
adding a provider to regenerate its `.g.dart`.

### Entities, DTOs, and Models

The domain and data layers use distinct types on purpose:

- **Entity** — a domain object with identity that persists across use cases
  (e.g. `User`). Pure Dart, no serialization.
- **DTO** — a data-transfer shape crossing a use-case boundary: the input to an
  operation (`EmailSignup`) or its result (`AuthToken`). Also pure Dart.
- **Model** — a data-layer type that adds JSON serialization
  (`fromJson`/`toJson`) on top of an entity or DTO. Models live in `data/` and
  keep serialization concerns out of the domain.

### Model styles: `extends` vs `freezed`

There are two ways to shape a model relative to its domain type:

- **`extends`** (default) — the model is a plain class that `extends` the domain
  type and adds `@JsonSerializable` + `fromJson`/`toJson` (e.g.
  `UserModel extends User`). Because the model *is* an instance of the domain
  type, a repository method typed to return the entity/DTO can return the model
  directly.
- **`freezed`** — the entity is a `@freezed` class implementing a shared
  `<Entity>IF` interface, and the model is a **separate** `@freezed` class
  implementing the same interface plus a `toEntity()` mapper. This decouples the
  JSON/data shape from the domain shape and gives you generated
  `==`/`copyWith`/pattern matching.

### Use Cases vs Services

The application is organized around **Use Cases**. The guiding rule:

> Use Cases orchestrate. Services perform work.

**Use Cases** express business intent — a complete operation initiated by a
user, API request, scheduled job, or external system. Ask *"What is the user
trying to accomplish?"* If the answer is Register, Login, Checkout, ShipOrder,
RefundPayment → create a Use Case. A Use Case may validate requests, load
entities, call repositories and services, coordinate business rules, manage
transactions, publish events, and return a response. It should stay small and
should **not** hold reusable logic that could be shared elsewhere.

**Services** encapsulate reusable capabilities. If the answer is Calculate,
Validate, Convert, Hash, Encrypt, Send, Store, Generate → create a Service.
There are three kinds:

- **Domain Services** — reusable business rules that don't belong to a single
  entity (`PricingService`, `TaxCalculator`, `FraudDetectionService`). They
  contain business logic but do **not** orchestrate repositories or workflows.
- **Infrastructure Services** — access to external systems
  (`EmailSender`, `PaymentGateway`, `FileStorage`, `Clock`). They implement
  interfaces defined in the application layer.
- **Technical Services** — reusable technical functionality with no business
  logic (`PasswordHasher`, `JwtTokenGenerator`, `CacheProvider`, `Logger`).

**Dependency direction:**

```
Controller → Use Case → Repositories / Domain Services / Infrastructure Services → Database / External APIs
```

- A Use Case may invoke multiple Services.
- A Service must **never** invoke a Use Case (and never another Use Case).
- Domain knows nothing about Application; Application knows nothing about
  Infrastructure; Infrastructure depends on Application interfaces.

**Anti-pattern — avoid God Services.** Do not create generic `UserService`,
`OrderService`, or `CustomerService` classes that accumulate `createOrder`,
`cancelOrder`, `refundOrder`, `sendReceipt`, `shipOrder`… — these violate the
Single Responsibility Principle and become hard to test. Prefer many small,
focused Use Cases composed from small, focused Services. When logic is reused
across Use Cases, extract it into a Service rather than duplicating it.

**Decision tree:**

1. Initiated by a user, API, message, or scheduled job? → **Use Case**
2. Reusable across multiple Use Cases? → **Service** (otherwise keep it inside the Use Case)
3. One focused business capability? → **Domain Service**
4. Interacts with external systems? → **Infrastructure Service**
